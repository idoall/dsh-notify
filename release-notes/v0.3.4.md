| **`0.3.4`** | **`0.1.7-rc.1`（最新 RC）** | 本次发布（`latest`） |

**兼容的最新 DSH 版本：`0.1.7-rc.1`**（`0.1.7` 系列的首个候选版本）。

### 为什么发这个版本

`0.3.3` 解决的是**「在 DSH `0.1.7` 上能不能用」**；本版解决的是**「什么时候提醒你」**——三处触发时序缺陷，由本插件与另一个通知插件 [dsh-messager](https://github.com/ly6170/dsh-messager) 的触发时机逐项对照后暴露。它们不影响加载，但会让你**漏收**或**早收**通知：

1. **失败可能永远不通知**：`agent/error` 此前只把错误消息记下来，等随后的 `turn/end` 才发卡；如果那一轮没有 `turn/end`，失败通知就彻底丢失。
2. **一次连续任务会发两张完成卡**：DSH 在同一个同步栈里发布 `agent/status: idle` 之后会立刻恢复排队的工作（`idle → running`）。由于 `session/event` 也要晚一个微任务处理，取消逻辑赶不上已经排队的投递，于是「从未真正停下来」的任务被宣布完成。
3. **通知最多晚 1.5 秒**：页面每 1500ms 轮询一次投递接口，即使它早已从 DSH 客户端状态里知道会话变了。

### 改了什么

- **失败在 DSH 报告的那一刻就投递。** `agent/error` 立即生成失败卡；随后到达的 `turn/end`（原因 `error`）派生出**同一个 `fail:<会话>:<轮次>` 身份**，因此它更新那张卡而不是再加一张——错误消息仍经原有路径合并进去。子代理的失败与子代理的完成一样保持安静。
- **同栈恢复的工作不再被当成已完成。** 延迟投递在真正执行时**复查会话是否仍为 `idle`**，于是 `running` 的取消能生效。这是**零延迟**的修法：没有防抖窗口，完成通知不会因此晚一秒。
- **页面已经知道的事，不再等下一次轮询。** 客户端订阅 `sessions.list` 与 Session 状态快照，变化时立即请求一次投递（前缘节流，200ms 一次）；后台标签页重新可见时也会立刻补拉一次。1500ms 定时器保留为兜底。同时投递游标改为只前进、不后退。
- 配置 schema、设置项与存储格式**未改动**。

### 谁受影响

- **等过「通知怎么还不来」的人：本版就是给你的。** 失败卡现在在错误发生时就出现；完成卡不再因为一次瞬时 `idle` 提前出现；通知从事件到上屏由「最多 1.5 秒」变为「下一次状态变化即到」。
- **开了「子任务 / 后台任务完成时通知」的人**：子代理**失败**仍然安静（与子代理完成一致），不会因为本版开始刷屏。
- **配置无需迁移**：`dataDir`、提示音、样式、位置等偏好原样继续生效。
- **仍在更早 DSH 上的人**：本版与 `0.3.3` 一样只支持 `0.1.7` 线；更早的 DSH（含 `0.1.6-alpha.1`）请继续用插件 `0.3.2`。

### 兼容性与升级

```sh
dsh plugin --profile web add @idoall/dsh-notify@0.3.4
```

- **宿主半边需要重启 `dsh web`** 才会加载本版——失败即时投递与同栈抖动修复都在宿主侧。
- **客户端半边刷新页面即生效**。
- 未配置绝对 `dataDir` 时，设置页仍显示「设置不落盘」，偏好只保存在当前进程。

### 验证

- `npm run verify`：静态检查（`tscheck.mjs` + `tsc --noEmit`）、**92/92** 测试、Host/Client 构建、npm 包前置检查。
- 新增 6 条回归用例：同栈 `idle → running` 抖动不出卡且最后真正结束的轮次只通知一次；失败在无 `turn/end` 时也会投递；失败有 `turn/end` 时**只有一张卡、同一个身份**；子代理失败保持安静；两条客户端用例按 `/pull` 请求数断言「会话状态变化」与「标签页重新可见」都会自己拉取。
- **其中 5 条行为用例在修复前的实现上全部失败**（用补丁回滚 `src/` 复现后确认），因此它们确实在守这条行为。
- **真机验证**：在一个隔离的 `DSH_HOME`（`/tmp` 下，不触碰使用者 profile）里，用官方 `web` / `headless` 模板建 profile，以 `link:` 安装本插件，在 DSH `0.1.7-rc.1` 上启动：
  - Host 半加载成功，`/plugins/dsh-notify/health` 返回 `guiAvailable: true`、`jobs: events`、`eventErrors: 0`。
  - 客户端 bundle 已注册，服务端下发的 bundle 中确实包含本版新增代码。
  - 真实会话（模型端点故意指向不可达地址）产生真实失败：观察器捕获到 `kind=failed` 记录在 `agent/error` 时刻投递，随后 `turn/end` 用**同一个 mergeKey** 再次投递——合并成一张卡，与设计一致。

### 限制

- **完成判定仍然严格**：只有 `turn/end` 的原因为 `completed` / `error` 才产生完成卡；`aborted` / `blocked` / `max-tokens` / `interrupted` 仍然安静。这是既有设计（与原生转圈停止一致），本版未改变。
- **通知记录仍是内存态**：已结算历史不会在刷新、浮层重挂载或 DSH 重启后重播；突发超过缓冲区容量（50 条）时，最旧的未投递记录会被丢弃。
- **同栈抖动修复依赖一个 DSH 不变量**：`agent/status: idle` 与紧随其后的 `running` 发布在同一个同步栈内（已在 `dsh-agent-loop` 的 `kick()` / `runMaintenance()` 收尾路径确认）。若未来 DSH 改为跨栈发布，需要重新评估——届时防抖才是更稳的兜底。
- **本版在隔离 profile 上完成真机验证**：使用者现有的 web profile 仍是 `0.3.3`，升级并重启 `dsh web` 后本版才生效。

<h3 id="en-v034">Plugin 0.3.4 — verified against DeepSeek Harness 0.1.7-rc.1 (the latest release candidate)</h3>

### Version matrix

| Plugin | Verified DeepSeek Harness | npm status |
| --- | --- | --- |
| **`0.3.4`** | **`0.1.7-rc.1` (latest RC)** | this release (`latest`) |
| `0.3.3` | `0.1.7-rc.1` | published |
| `0.3.2` | `0.1.6-alpha.1` | published |
| `0.3.1` | `0.1.6-alpha.1` | published |
| `0.3.0` | `0.1.6-alpha.1` | published |

**Latest compatible DeepSeek Harness: `0.1.7-rc.1`** — the first release candidate of the `0.1.7` line.

### Why this release exists

`0.3.3` answered "does it work on DSH `0.1.7`". This one answers **"when does it tell you"** — three trigger-timing defects, found by comparing this plugin's trigger semantics against another notification plugin, [dsh-messager](https://github.com/ly6170/dsh-messager). None of them breaks loading, but each one either loses a notification or sends it too early:

1. **A failure could never be announced.** `agent/error` only remembered the message for the `turn/end` that was expected to follow. A failure whose turn never ended was never announced at all.
2. **One continuous task could produce two completion cards.** DSH publishes `agent/status: idle` and resumes queued work (`idle → running`) in the same synchronous stack. Because every `session/event` is also handled one microtask later, the cancellation could not outrun the delivery already queued for that idle — so a task that never stopped was announced as finished.
3. **A notification could arrive up to 1.5 s late.** The page polled the delivery route every 1500 ms even when it had already learned from DSH's client-side session state that something had changed.

### What changed

- **A failure is delivered the moment DSH reports it.** `agent/error` now produces the failure card immediately; the `turn/end` that follows (reason `error`) derives the **same `fail:<session>:<turn>` identity**, so it updates that card instead of adding a second one — the error message is still merged onto it through the existing path. A subagent failure stays as quiet as a subagent completion.
- **Work that resumes in the same stack is no longer announced as finished.** The deferred delivery re-checks that the session is still `idle` when it actually runs, so the `running` cancellation wins. This is a **zero-latency** fix: no debounce window, and no completion is delayed by a second because of it.
- **What the page already knows no longer waits for the next tick.** The client subscribes to `sessions.list` and the Session status snapshot and requests a delivery as soon as either changes (leading-edge throttled to one per 200 ms); a background tab also catches up the moment it becomes visible again. The 1500 ms interval stays as the fallback, and the delivery cursor can now only move forwards.
- The config schema, settings, and stored format are **unchanged**.

### Who is affected

- **Anyone who has waited for a notification that never came: this release is for you.** A failure card now appears when the failure happens; a completion card no longer appears early because of a transient `idle`; and a notification goes from "up to 1.5 s" to "as soon as the state change is seen".
- **Anyone who enabled "notify on subtask / background task completion":** a subagent **failure** stays silent, exactly like a subagent completion, so this release does not start flooding you.
- **No migration.** `dataDir`, sound, style, position, and every other preference keep working as they are.
- **Anyone on an older DSH:** like `0.3.3`, this release supports the `0.1.7` line only. On anything earlier (including `0.1.6-alpha.1`) stay on plugin `0.3.2`.

### Compatibility and upgrade

```sh
dsh plugin --profile web add @idoall/dsh-notify@0.3.4
```

- **The Host half needs a `dsh web` restart** to load this version — both the immediate-failure delivery and the same-stack flap fix live on the Host side.
- **The client half takes effect on a page refresh.**
- Without an absolute `dataDir`, the settings page still reports "settings are not persisted" and preferences live only for the current process.

### Verification

- `npm run verify`: static source checks (`tscheck.mjs` + `tsc --noEmit`), **92/92** tests, Host/Client build, and npm package precondition checks.
- Six new regression tests: a same-stack `idle → running` flap emits no card and the turn that really ends last is announced exactly once; a failure with no following `turn/end` is still delivered; a failure whose turn does end stays one card with one identity; a subagent failure stays silent; and two client tests count `/pull` requests to assert that both a session-state change and a visible-again tab pull on their own.
- **Five of those behaviour tests fail against the previous implementation** (confirmed by reverting `src/` with a patch), so they really do guard the behaviour.
- **Real-machine verification:** in an isolated `DSH_HOME` under `/tmp` (the user's profile is never touched), profiles were created from the shipped `web` and `headless` templates, this plugin was installed with `link:`, and DSH `0.1.7-rc.1` was booted:
  - The Host half loaded: `/plugins/dsh-notify/health` answered with `guiAvailable: true`, `jobs: events`, `eventErrors: 0`.
  - The client bundle was registered, and the bundle the server handed out really did contain this version's new code.
  - A real session (its model endpoint deliberately unreachable) produced a real failure: the observer captured a `kind=failed` record delivered at `agent/error` time, then a second delivery from `turn/end` with the **same mergeKey** — one card, exactly as designed.

### Limitations

- **Completion is still strict:** a completion card is only produced for a `turn/end` whose reason is `completed` / `error`. `aborted`, `blocked`, `max-tokens`, and `interrupted` stay silent. That is the existing design (it matches the native spinner stopping) and this release does not change it.
- **Notification records remain memory-only:** settled history is not replayed after a refresh, an overlay remount, or a DSH restart, and a burst larger than the buffer (50 records) drops the oldest undelivered record.
- **The same-stack fix relies on a DSH invariant:** `agent/status: idle` and the `running` that immediately follows are published in one synchronous stack (confirmed in `dsh-agent-loop`'s `kick()` / `runMaintenance()` exit paths). If DSH ever publishes them from different stacks, this needs re-evaluation — a debounce would then be the sturdier fallback.
- **Real-machine verification was done on an isolated profile:** an existing web profile still runs `0.3.3` until it is upgraded and `dsh web` is restarted.
