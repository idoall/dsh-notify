<h3 id="cn-v032">完成通知与原生会话状态同步</h3>

### 这次解决了什么

`0.3.2` 修复的是绿色“任务完成”Toast 的完成判定，而不是通知样式或浏览器显示问题。此前插件以 `turn/end` 配合延迟策略推测任务是否结束；但 DSH 右侧文本看起来已经完成时，左侧原生会话仍可能处于运行状态、继续执行工具调用、goal 自动续跑或排队的后续轮次。两套生命周期不一致会造成两类相反问题：

1. **漏通知**：原生会话最终已经完成（左侧转圈停止 / 完成状态出现），插件之前的候选却被后续状态取消或一直滞留，因此右上角没有绿色 Toast。
2. **重复通知**：修复漏通知后，如果计划待审或执行审批让同一任务出现一次短暂 idle，插件可能把这个“等待用户决定”的中间暂停和批准后的实际工作完成都当成独立任务，显示两张同会话的绿色卡。
3. **普通问题直接结束时又漏通知**：为抑制上面的重复卡，不能把所有交互 turn 一律静默。普通“需要回复”在用户回答后可以直接结束任务；若一并抑制，就会出现左侧显示完成、右上角没有 Toast 的回归。

### 修复方式

- **完成时机与 DSH 原生状态对齐**：`turn/end` 现在只登记完成候选。只有所属 Agent 报告 `agent/status: idle` 后才投递绿色完成卡，这与 DSH 左侧会话树转圈真正停止是同一个权威状态。新的 `running` 状态会取消旧候选，所以不会在任务继续执行时过早通知。
- **计划待审与执行审批不再重复完成**：`exit_plan_mode`（计划待审）和 `approval/asked`（执行审批）被视作控制门。它们暂时进入 idle 仅表示正在等用户决定，不是任务完成；批准或回答后继续执行的非交互工作轮才会产生唯一的一张绿色完成卡。
- **普通“需要回复”直接收尾仍会通知**：`ask_user_question` 与控制门明确区分。若用户回答后任务直接进入原生 idle，插件会发送一张绿色完成卡；若回答后继续运行，则旧候选会被取消，最终仍只在真正结束时发送一次。

### 对使用者的可观察行为

- 右侧文本先结束、左侧仍转圈时：不会提前出现绿色完成 Toast。
- 左侧转圈停止、会话真正完成时：出现一张绿色“任务完成”Toast。
- 计划待审或执行审批后继续工作：不会先后出现两张针对同一连续任务的绿色卡。
- 普通“需要回复”回答后直接结束：不会因为去重逻辑而丢失完成卡。

### 验证

- 新增原生生命周期回归：native `running` 时不发完成；转为 native `idle` 后恰好发一次。
- 新增计划待审回归：中间交互暂停与批准后的继续工作合计只产生一张完成卡。
- 新增普通问题回归：回答普通问题后若直接结束，仍恰好产生一张完成卡。
- 完整发布验证通过：静态检查、**84 项自动化测试**、Host/Client 构建及 npm 包前置检查。

### 已知边界

- 通知记录仍是进程与页面内存状态；已结算历史不会在刷新、浮层重挂载或 DSH 重启后重播。
- DSH 重启会清空原生运行时 pending interaction。重启前尚未处理、且新 Host 不再报告的交互不能恢复原生左侧橙点或 Toast；这是 DSH 原生状态恢复边界，插件不会伪造或持久化该状态。

<h3 id="en-v032">Completion notifications synchronized with native session state</h3>

### What this release solves

`0.3.2` fixes the semantic definition of a green **Task completed** Toast. This is not a styling or browser-display change. Earlier releases inferred completion from `turn/end` plus a delay. A response can look finished in the conversation while native DSH is still running tools, continuing a goal, or scheduling a follow-up turn, so that inferred lifecycle could disagree with the session tree.

That mismatch produced three related failures:

1. **Missing completion Toasts**: the native session could really finish (its spinner stops and its completed state appears) after the plugin's candidate was cancelled or stranded, leaving no green Toast.
2. **Duplicate completion Toasts**: after aligning with native idle, a plan review or execution approval could create a temporary idle pause. Treating both that user-decision pause and the later real work completion as tasks showed two green cards for one continuous task.
3. **A regression for directly resolved ordinary questions**: suppressing every interactive turn fixed the duplicate but also suppressed a valid case where a user's answer to an ordinary question directly finished the task. Native DSH showed the completed session, but no Toast was delivered.

### How it is fixed

- **Completion timing follows native DSH state**: `turn/end` now records a candidate only. The green card is delivered after the owning Agent reports `agent/status: idle`, which is the same authority that stops the native session-tree spinner. A new `running` transition cancels an older candidate, preventing premature delivery while work continues.
- **Plan reviews and execution approvals no longer duplicate completion**: `exit_plan_mode` and `approval/asked` are control gates. Their temporary idle state means that DSH is waiting for a decision, not that the task is complete. The later non-interactive work turn delivers the sole green card.
- **An ordinary question can directly complete work**: `ask_user_question` is intentionally distinct from a control gate. If the user's answer directly brings the task to native idle, one green card is delivered. If work resumes instead, the candidate is cancelled and the final work turn remains the only completion notification.

### Observable behavior

- When conversation text appears complete but the session-tree spinner is still moving, no green completion Toast appears early.
- When the spinner stops and the native session is truly complete, one green **Task completed** Toast appears.
- A plan review or execution approval followed by more work produces one green card for the continuous task, not two.
- An ordinary **Needs reply** interaction that directly finishes work still produces one green card.

### Verification

- Native lifecycle regression: no completion while native status is `running`; exactly one after native `idle`.
- Plan-review regression: an intermediate decision pause plus approved follow-up work produces one completed card in total.
- Ordinary-question regression: an answered question that directly finishes work still produces exactly one completed card.
- Full release verification passed: static checks, **84 automated tests**, Host/Client build, and npm package precondition checks.

### Known boundary

- Notification records remain process- and page-memory state. Settled history is not replayed after a refresh, overlay remount, or DSH restart.
- A DSH restart clears native in-process pending interactions. If the new Host no longer reports an interaction that was pending before restart, the plugin cannot restore its native amber sidebar marker or Toast. That is a native DSH state-recovery boundary; this plugin does not fabricate or persist it.
