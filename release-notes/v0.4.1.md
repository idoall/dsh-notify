兼容性跟进版：让插件在 DeepSeek Harness `0.2.0-rc.1` 上继续加载并正常运行，**除兼容性声明外没有任何代码改动**。

<h3 id="cn-v041">🔌 兼容性</h3>

- 兼容范围由 `>=0.1.7-rc.1 <0.2.0` 放宽为 `>=0.1.7-rc.1 <0.3.0`：`dsh.engines.dsh` 与四个 `@deepseek-ai/dsh-*` peer 同步更新。
- `dsh.compatibility.dshReleases` 新增 `0.2.0-rc.1`；`0.1.7-rc.1`、`0.1.7-rc.2` 继续声明兼容。
- **旧声明会在 `0.2.0` 正式版上把插件挡在 profile 之外。** DSH 在加载 profile 时按 peer 范围拒绝不兼容的 bundle（本机运行中的 `dshmarket`、`@nanmicoder/dsh-agent-teams`、`dsh-code-index` 就是这样被跳过的）。`0.2.0-rc.1` 作为预发布版恰好仍落在 `<0.2.0` 之内所以现在能加载，而 `0.2.0`、`0.2.1` 不能。
- 插件绑定的接口在 `0.2.0-rc.1` 上均未变化：宿主事件（`agent/status`、`session/event`、`approval/request`、`user-questions/request`、`goal/activation-changed`、`agent/error`、`workflow/end`）、Web 路由与 `connection` 鉴权、`jobs` 事件流、客户端 `slots` 的两个座位、`--dsw-alias-*` 主题 token。

<h3 id="cn-v041">✅ 验证</h3>

- `npm run verify`：静态检查、**110/110** 测试、Host/Client 构建、npm 包前置检查（含兼容声明一致性）。
- **真机验证**：在 `/tmp` 下隔离的 `DSH_HOME`（不触碰使用者 profile）中用官方 `web` 模板建 profile，以 `link:` 安装本插件并启动 DSH `0.2.0-rc.1`：
  - profile 组合包含 `dsh-notify` 行，未被兼容性门禁拒绝。
  - `/plugins/dsh-notify/health` 返回 `guiAvailable: true`、`eventErrors: 0`；`/config`、`/pull`、`/sounds`、`/update`（走真实 npm registry）均正常。
  - 浏览器中「设置 → 通知」实际渲染，自测通知浮层正常显示，页面无报错。
- 反证：同一套 peer 范围在真实 semver 下，对 `0.2.0` 与 `0.2.1` 判定为不满足（旧声明），对 `0.2.0-rc.1` 满足——即旧声明确实会在 `0.2.0` 正式版上丢弃插件。

### 升级

```sh
dsh plugin --profile web add @idoall/dsh-notify@0.4.1
```

宿主半边需重启 `dsh web` 才生效；客户端半边刷新页面即生效。

<h3 id="en-v041">🔌 Compatibility</h3>

A compatibility follow-up: the plugin keeps loading and running on DeepSeek Harness `0.2.0-rc.1`, with **no code change beyond the compatibility declarations**.

- The supported range widens from `>=0.1.7-rc.1 <0.2.0` to `>=0.1.7-rc.1 <0.3.0`; `dsh.engines.dsh` and all four `@deepseek-ai/dsh-*` peers move together.
- `dsh.compatibility.dshReleases` gains `0.2.0-rc.1`; `0.1.7-rc.1` and `0.1.7-rc.2` stay declared compatible.
- **The old declaration would have dropped the plugin the moment `0.2.0` shipped.** DSH refuses an incompatible bundle at profile load by peer range — that is how `dshmarket`, `@nanmicoder/dsh-agent-teams`, and `dsh-code-index` are skipped on this machine today. `0.2.0-rc.1` happens to fall inside `<0.2.0` because it is a prerelease, so it loads; `0.2.0` and `0.2.1` would not.
- Every interface the plugin binds is unchanged in `0.2.0-rc.1`: the Host events (`agent/status`, `session/event`, `approval/request`, `user-questions/request`, `goal/activation-changed`, `agent/error`, `workflow/end`), the Web routes and `connection` authorization, the `jobs` event stream, the two client `slots` seats, and the `--dsw-alias-*` theme tokens.

<h3 id="en-v041">✅ Verification</h3>

- `npm run verify`: static source checks, **110/110** tests, Host/Client build, and npm package precondition checks (including compatibility-declaration consistency).
- **Real-machine verification** in an isolated `DSH_HOME` under `/tmp` (the user's profile is never touched): a profile from the shipped `web` template, the plugin installed with `link:`, and DSH `0.2.0-rc.1` booted:
  - the composed profile contains the `dsh-notify` row and the compatibility gate does not refuse it;
  - `/plugins/dsh-notify/health` answers `guiAvailable: true`, `eventErrors: 0`, and `/config`, `/pull`, `/sounds`, `/update` (reaching the real npm registry) all work;
  - **Settings → Notifications** renders in the browser, the self-test toast stack displays, and the page reports no errors.
- Counter-proof: under the real semver evaluation, the same peer ranges do **not** satisfy `0.2.0` or `0.2.1` (the old declaration) while they do satisfy `0.2.0-rc.1` — so the old ceiling really would have dropped the plugin on the `0.2.0` release.

### Upgrade

```sh
dsh plugin --profile web add @idoall/dsh-notify@0.4.1
```

The Host half needs a `dsh web` restart; the client half takes effect on a page refresh.
